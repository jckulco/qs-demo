# Job: JOB_09_TwoSourceMatch — ✅ COMPLETE AND VALIDATED

**Goal:** cross-check `customers_crm_clean.csv` (Reference/Source A)
against `customers_erp_standardized.csv` (Data/Source B) to determine
which customers exist in both systems and which are exclusive to each
one.

This was, by far, the most complex step in the project: it chained
6 distinct problems before running clean. They're all documented here
because each one reveals a real constraint of the `Two-Source Match`
stage that wasn't anticipated in the original theoretical plan
(`06-two-source-match.md`).

## Match Specification: `twosource_match_crm_erp`

- Match type: **"Two-source one-to-one"** (each record from one source
  pairs with, at most, one record from the other — not "many-to-one").
- Input schema on the Data side imported from a **manual Data
  Definition** (`customers_erp_standardized`, 5 columns), not directly
  from the CSV — see finding #25.
- Blocking: `Block_ZIP` (CHARACTER) on `ZIP_STD` ↔ `ZIP_STD`.
- Matching columns:

| Name | Type | Data (ERP) | Reference (CRM) | mProb | uProb |
|---|---|---|---|---|---|
| Match_PrimerNombre | UNCERT | MatchPrimerNombre_MXNAME_ERP | MatchPrimerNombre_MXNAME | 0.9 | 0.01 |
| Match_Apellido | UNCERT | MatchApellido_MXNAME_ERP | MatchApellido_MXNAME | 0.9 | 0.01 |
| Match_Calle | UNCERT | MatchNombreCalle_MXADDR_ERP | MatchNombreCalle_MXADDR | 0.9 | 0.01 |
| Match_Telefono | CHAR | TELEPHONE_STD | PHONE_STD | 0.9 | 0.01 |

- Final cutoffs: **Match = 11**, Clerical = 9, Duplicate = 20 (the
  Duplicate field has no real effect in one-to-one mode, but the UI
  requires `Match ≤ Duplicate` to save — see finding #30).

## Real problems found and solved (in chronological order)

### 25. The stage needs 4 input links, not 2

**Symptom:** `CDIWA0041E: The stage Twosource_Match_1 requires at least 4
input links.`

**Cause:** unlike One-Source Match (2 ports: input + frequency),
Two-Source Match expects **4 fixed-name ports**: `Data`, `Reference`,
`DataFreq`, `RefFreq` — each source needs its own frequency input, not a
combined one.

### 26. The `Funnel` stage doesn't union mismatched schemas — it only concatenates identical ones

**Symptom:** when combining CRM+ERP with a Funnel before a single Match
Frequency, columns with the `_ERP` suffix would disappear from the output
schema depending on the order the links were connected in — erratic,
non-deterministic behavior.

**Root cause:** `Funnel` isn't a "schema union" stage (like a `UNION ALL`
that fills mismatched columns with NULL) — it just concatenates streams
using one of the input links' schema as the base, dropping whatever
doesn't match. When the two sources have differently-named columns (as
here, after the `_ERP` renaming), Funnel is the wrong tool.

**Solution:** abandon the "combine and compute frequency once" approach
(which did work in `JOB_06_MasterMerge`, because there both sources DID
share 99 identical columns) and instead generate **two fully independent
frequency files**, one per source — see
`docs/06b-match-frequency-twosource.md`.

**Key project lesson:** a Funnel is only safe when the sources share the
exact same schema (like CRM survivors + Nonmatched in Job 6). As soon as
column names differ between sources, you need to generate separate
outputs instead of forcing a combination.

### 27. Name collision: `qsMatchType` generated by the stage clashes with the column inherited from the CRM

**Symptom:** `FATAL: Source field "qsMatchType" already exists in the
adapter.`

**Cause:** `customers_crm_clean.csv` carries the `qsMatchType`/
`qsMatchDataID` columns as leftovers from the earlier One-Source Match
(Step 4/5). The `Two-Source Match` stage itself generates its own
internal columns with those same names — a direct collision.

**Solution:** a `Transformer_2` on the CRM branch that drops
`qsMatchType` and `qsMatchDataID` (and any other `qsMatch*` column)
before they reach the stage — those columns were internal diagnostics
from an earlier matching process and add nothing to this new cross-check.

### 28. The Match Specification's schema import wizard re-infers types from the CSV's content, ignoring the real declared schema

**Symptom:** when importing `customers_erp_standardized.csv` as the
Match Spec's Input schema, `TELEPHONE_STD` and `ZIP_STD` showed up as
`BIGINT`/`INTEGER`, despite being correctly declared `VARCHAR` in
`JOB_07`'s real `Sequential file`.

**Cause:** this wizard's importer doesn't read the file's declared
schema — it sniffs the type directly from the content. Since the 8 ERP
records have those columns fully populated with digits only (with no
non-numeric value to "give away" that it's text), the sniffer assumes a
numeric type. The same problem didn't happen with `PHONE_STD` on the CRM
side because that column does have the literal value `"NULL"` in 2
records, forcing the sniffer to infer `VARCHAR`.

**Solution:** manually create a **Data Definition** (asset type "Data
definition," not "Match specification") with the 5 needed columns,
explicitly typed as `VARCHAR(1024)`, and use it as the source for the
Match Spec's Input schema instead of pointing directly at the CSV. A Data
Definition was needed for each side (`customers_erp_standardized` with
`_ERP` columns, `customers_crm_clean` with no suffix) so both sides of
the spec imported the correct types.

### 29. Renaming a column in a Transformer without updating the Match Spec or the Data Definition feeding it triggers a cascade of errors

A full sequence of three related errors, each fixed without realizing the
next one was still lurking:

1. `Unable to locate column MatchPrimerNombre_MXNAME` — the Match Spec
   was still looking for the old (unsuffixed) name on the Data side after
   the Transformer had already renamed it to `_ERP`.
2. When editing the Match Spec directly, the "Data column" dropdown
   didn't offer the `_ERP` name as an option — because the **Data
   Definition** feeding the spec's Input schema hadn't been updated
   either.
3. After fixing the Data Definition and the Match Spec, a new error:
   `Frequency information ... not present in the data frequency file` —
   because the frequency file (`JOB_08`) didn't have entries for the
   `_ERP` name yet either, generated before the rename.

**Consolidated lesson:** renaming a column anywhere in this chain
(Transformer → Data Definition → Match Specification → frequency file)
has to propagate to **all four** places. There's no automatic sync
between them — each one lives in a different asset or job, edited
separately.

### 30. The Match cutoff was calibrated against a theoretical plan, not against the real computed weights

**Symptom:** with `Match cutoff = 13.0` (copied from the theoretical plan
`06-two-source-match.md`), the 6 pairs that should have been "Match" all
fell into `Clerical`, with real weights between 11.59 and 12.29.

**Solution:** lower the Match cutoff to `11` (below the lowest observed
weight, with margin). When trying to save it, a UI cross-validation
appeared: `Match cutoff must be <= Duplicate cutoff` — resolved by
raising `Duplicate` to a high value (`20`) first, then lowering `Match`,
in that specific order (changing `Match` before `Duplicate` triggers the
inverse error: `Duplicate cutoff must be >= Match cutoff`). The
`Duplicate` field has no functional effect in "one-to-one" mode — it only
exists to satisfy the UI's validation.

**Lesson:** a theoretical plan's cutoffs are only a starting point — they
always need to be validated against the real weights the engine produces
with the real data, and adjusted based on the observed result, not
assumed to work the same as the theoretical value.
